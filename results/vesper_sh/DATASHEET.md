# Datasheet for VESPER-SH

This datasheet follows the schema proposed by Gebru et al., *"Datasheets for
Datasets"* (CACM 2021). It documents motivation, composition, collection
process, preprocessing/labeling, intended uses, distribution, maintenance,
and limitations for **VESPER-SH**, a labeled, multi-modal smart-home
security benchmark dataset.

Dataset authors: **the VESPER-SH authors (anonymized for review)**.

Status: this datasheet describes the dataset's design and the pipeline that
produces it. Composition figures marked `<filled from build output: ...>`
are placeholders — the generation run that populates `episodes/` has not
been executed yet at the time this datasheet was written, so no counts are
asserted. Once the dataset is built, those placeholders should be replaced
with the real numbers emitted by `scripts/dataset/run_baselines.py` and
`scripts/dataset/build_dataset.py` (composition table, `baseline_results.json`).

---

## 1. Motivation

**For what purpose was the dataset created?**
Network- and system-intrusion-detection datasets for industrial control
systems — SWaT, WaDI, HAI — are heavily cited because the *dataset itself*
is the contribution: a labeled, reusable capture that anomaly/intrusion
detection researchers can train and evaluate on. Each of those is a single,
long, continuous capture of one physical environment, so they cannot pose a
cross-environment generalization question. VESPER-SH exists to fill that
gap for the smart-home domain: it asks whether a detector trained on some
homes and resident behaviors generalizes to homes and residents it has
never seen. It is produced by a reproducible, regenerable testbed (LLM-driven
embodied residents acting in simulated homes, coupled to firmware-in-the-loop
simulated devices and an emulated Wi-Fi network with a scheduled, precisely
timestamped attack suite), so — unlike a one-off physical capture — the
generation process itself is part of the artifact.

**Who created it, and on whose behalf?**
The VESPER-SH authors (anonymized for review), as part of the VESPER
research testbed. No third-party crowdworkers, vendors, or data-collection
services were involved; every event in the dataset is emitted by the
authors' own simulation/emulation pipeline.

**Who funded it?**
Withheld during double-blind review; will be disclosed in the camera-ready
acknowledgments.

## 2. Composition

**What do the instances represent?**
The dataset has two nested units of analysis:
- An **episode** = one `(home, resident model, run)` triple: a continuous,
  dual-vantage network capture plus an activity/device event log covering
  one simulated Habitat home, driven by one resident LLM policy, for one
  run. Episodes are the unit of cross-environment generalization (a whole
  episode belongs to exactly one home, so home-disjoint splits are
  well-defined).
- A **window** = one 1-second, non-overlapping time slice within an
  episode, with an activity/device/network feature vector and a label. This
  is the unit consumed by the baseline detectors.

**How many instances are there?**
**60 episodes** across **20 homes × 3 resident LLM policies** (qwen2.5-7b,
llama-3.1-8b, gemma-2-9b), 1 run each. Of these, **47 carry network capture**
and **43 contain at least one labeled attack window**; the 13 final episodes
fell outside the VM's capture window (a fixed operational limit, see §8), but
all 20 homes are network-covered via the qwen and llama residents. The
generator is open and extends to more homes/residents.
- Total 1-second windows: **17,823**
- Windows per split (`splits/by_home/{train,test}`): **12,070 train / 5,753 test**
- Per-class window counts: **benign 14,664; lan_scan 1,808; beacon_flood 393;
  evil_twin 365; arp_spoof 361; deauth 232** (benign-dominant, ~82%)
- Approximate total captured duration: **≈8 hours** of coupled activity +
  scheduled attacks (episodes are on the order of minutes each — see §8).

**Does the dataset contain all possible instances, or a sample from a
larger population?**
It is a deliberately constructed benchmark, not a probability sample of a
"population" of real smart homes. Homes are a fixed, enumerable set of
Habitat 3.0 scene instances chosen for layout/behavior diversity; resident
behavior is generated by running each of a fixed roster of resident LLM
policies once (by default) per home. Cross-environment generalization is
evaluated via held-out homes/residents (see §7 of the README), not via
statistical sampling guarantees over a larger population.

**What does each instance consist of?**
Each episode directory (`episodes/<home>__<model>__<run>/`) contains:
- Raw material: `events.jsonl` (activity/device events, canonical Mac
  clock), `attack_schedule.jsonl` (ground-truth attack injection intervals),
  `ap.pcap` (router/AP-vantage capture), `rf.pcap` (RF-monitor-vantage
  capture).
- Derived, ML-ready material: `windows.parquet` (1-second feature table),
  `labels.csv` (per-window label), `meta.json` (episode metadata + clock
  offset). See `schema.md` for the exact column-level documentation.

**Is there a label or target associated with each instance?**
Yes. Each window in `labels.csv` has a multiclass `label` (`benign` or one
of 5 attack classes) and a derived `binary` indicator (0 = benign, 1 =
attack). Labels are ground truth by construction: they come from the
recorded attack-injection schedule, not from a learned or human-annotated
process (see §4).

**Is any information missing from individual instances?**
Episodes whose clock-synchronization events don't match between the Mac
and VM sides (or that have no events/frames at all) fail an integrity check
at export time and are dropped rather than silently included with corrupted
timestamps: `export_episode.export()` raises on a broken/mismatched sync or
an empty episode, and the batch driver (`build_dataset.py`) catches this
per-episode-directory, prints a `SKIP <name>: <reason>` line, and continues
rather than aborting the whole run. There is no interpolation or imputation
of missing frames/events within a retained episode — a window with zero
observed events/frames in `[t, t+1)` simply has all-zero activity/device/network
counts for that window (this is a true "nothing happened here" observation
given the pipeline's instrumentation, not a missing-value sentinel).

**Are relationships between instances made explicit?**
Yes, in two ways. (1) Episode grouping: the `<home>__<model>__<run>`
directory name and the corresponding `home`/`model`/`run` fields in
`meta.json` make the home/resident/run structure explicit, and the loader's
`groups` return value (home id) supports group-aware cross-validation. (2)
Within-episode ordering: windows are strictly ordered and contiguous by
`window_idx`/`ts` (1-second cadence, no gaps in the index), so temporal
relationships within an episode are recoverable directly from the table.

**Are there recommended data splits?**
Yes — `splits/by_home/{train,test}.txt` (cross-home generalization, home-disjoint,
~2/3 train / ~1/3 test), `splits/by_resident/{train,test}.txt` (train on 2 of
the 3 resident LLM policies, test on the held-out third), and
`splits/folds.json` (k=5 grouped-by-home cross-validation folds, no home in
both the train and test side of any fold). See the README and schema.md for
exact generation semantics.

**Are there any errors, sources of noise, or redundancies?**
The network feature block is extracted via `tshark`-parsed pcap fields;
malformed or unparseable frame rows are dropped rather than raising (a
frame whose `frame.time_epoch` doesn't parse as a float is skipped). The
`net_data` feature name is a naming artifact worth flagging here as a
potential source of confusion (see `schema.md`): it is a plain AP-vantage
frame count, not an 802.11 data-subtype filter, because `ap.pcap` is a
router/LAN-side capture, not an 802.11 monitor capture. No duplicate
episodes are expected (episode identity is the `home`/`model`/`run` triple),
but the dataset does not currently de-duplicate at the window level beyond
that.

**Is the dataset self-contained, or does it rely on external resources?**
Self-contained for consumption: `windows.parquet` + `labels.csv` +
`meta.json` are enough to reproduce the reported baselines. The raw
material (pcaps, event logs) is also included per episode for researchers
who want to re-derive features differently. The dataset does *not* embed
copies of the Habitat 3.0 scene assets, the resident LLM weights, or the
firmware/Wi-Fi emulation stack — those are part of the (separately
released) VESPER testbed code, needed only to *regenerate* or *extend* the
dataset, not to consume it.

**Does the dataset contain data that might be considered confidential?**
No. All network identities (MAC/IP addresses, SSIDs), device states, and
"resident" behavior are synthetic, generated inside an isolated
emulation/simulation environment. No real home network, real device, or
real occupant is represented.

**Does the dataset contain data that might be offensive, insulting,
threatening, or that might cause anxiety?**
No.

**Does the dataset relate to people?**
Indirectly, through simulated behavior only — not through data about real
people. "Residents" are LLM-driven embodied agents (autonomous policies)
acting in a simulated Habitat 3.0 home; the activity traces (motion, room
transitions, device interactions) logged in `events.jsonl` are synthetic
behavior produced by a resident policy, not recordings or logs of real
human occupants. No personally identifiable information is collected, and
no human-subjects/IRB review was required or sought, because no human
subjects are involved in producing the data.

## 3. Collection Process

**How was the data associated with each instance acquired?**
Everything is generated, not observed-and-recorded from a pre-existing
source. A resident LLM policy drives an embodied agent through a simulated
Habitat 3.0 home; its 3D activity is coupled over a bridge to a
firmware-in-the-loop simulated smart-home device network and an emulated
802.11 Wi-Fi network (`mac80211_hwsim` + `wmediumd`), with real
SmartThings/Matter/Home-Assistant-style connector logic driving device
state and automation ("tap") firing. All of this is instrumented directly:
an in-process JSONL event logger on the simulation side, and a device-agent
logger plus continuous dual-vantage `tshark` capture (`ap.pcap` on the
router/AP interface, `rf.pcap` on a monitor-mode RF interface) on the
network-emulation side.

**What mechanisms or procedures were used to collect the data?**
- **Structured event logging:** a JSONL logger subscribed to the
  simulation's event bus and sensor bus writes one line per activity/device
  event (`motion_detected`, `agent_entered_room`/`agent_left_room`,
  `door_opened`, `device_state_changed`/`state_change`, `tap_fired`,
  `firmware_state_update`), timestamped on the simulation host's clock.
- **Dual-vantage capture:** `tshark` runs continuously for the whole
  episode on both the AP/router interface and a monitor-mode RF interface,
  so LAN-layer and RF/management-layer traffic are captured from the
  vantage point a corresponding real-world defender would actually have
  (see §4 of the attack taxonomy in the README).
- **Scheduled attack injection:** attacks are injected by an automated
  attack loop on a fixed schedule (not triggered by, or reactive to,
  detector output), cycling the 5 attack classes with benign gaps between
  rounds; each injection's class, start time, and end time is logged to
  `attack_schedule.jsonl`. Because injection is scheduled and logged rather
  than inferred after the fact, labels are exact interval ground truth, not
  heuristically assigned.
- **Clock synchronization:** the simulation host and the network-emulation
  host run on different clocks. Bridge-forwarded events are logged with a
  matchable sequence number on both sides; the offset is computed as the
  median of `(far_side_ts - near_side_ts)` over sequence-matched events, and
  every downstream timestamp (pcap frames, the attack schedule) is mapped
  onto the simulation host's clock via that offset before windowing. No NTP
  or wall-clock assumption is required. If the two sides' sync logs exist
  but no sequence numbers match, export fails loudly (`ValueError`) instead
  of silently producing a misaligned episode.

**If the dataset is a sample, what was the sampling strategy?**
Not applicable in the survey-sampling sense — see §2 ("deliberately
constructed benchmark, not a probability sample"). The home set and
resident-model roster are chosen by the authors for diversity, not drawn at
random from a larger corpus at generation time.

**Who was involved in the data collection process, and how were they
compensated?**
No human data-collection labor: the entire pipeline (activity generation,
attack injection, capture, logging) is automated. No crowdworkers or paid
annotators were involved at any stage.

**Over what timeframe was the data collected?**
A single generation run on 2026-07-14 (~11 hours wall-clock; ~8 hours of
coupled capture). Because the
testbed is reproducible, "collection" is really "generation," and the
pipeline can be re-run to produce additional episodes at any time; this
field records when the specific release's episodes were generated, not a
naturally-occurring collection window.

**Were any ethical review processes conducted?**
No IRB or human-subjects ethical review was sought, because the dataset
contains no data about real people, real networks, or real devices (see
§2). The attack traffic is synthetic and confined to an isolated
emulation/simulation environment; no real infrastructure is targeted or
affected.

## 4. Preprocessing, Cleaning, and Labeling

**What preprocessing/cleaning/labeling was done?**
1. **Clock alignment:** all raw timestamps are mapped onto one canonical
   clock via the offset described in §3.
2. **Windowing:** each episode's canonical timeline is cut into
   non-overlapping, half-open 1-second windows `[t, t+1)`, spanning
   `floor(min timestamp)` to `ceil(max timestamp)` across all of that
   episode's events and frames.
3. **Feature extraction:** for each window, three modality blocks are
   computed independently and merged — activity (from `events.jsonl`),
   device/automation (from `events.jsonl`), and network (from `ap.pcap` +
   `rf.pcap`, parsed via `tshark`). Exact fields are in `schema.md`.
4. **Labeling:** for each window, the attack schedule (mapped to the
   canonical clock) is checked for any injection interval overlapping
   `[t, t+1)` (`start < t+1 and end > t`); the window is labeled with that
   attack's class, or `benign` if no injection overlaps. Because the
   injection schedule is constructed so that attack rounds don't overlap
   each other, the earliest-starting match is used as a tie-break rule
   rather than being expected to fire in practice.

**Was the "raw" data saved in addition to the preprocessed data?**
Yes. Each episode directory retains the raw `events.jsonl`,
`attack_schedule.jsonl`, `ap.pcap`, and `rf.pcap` alongside the derived
`windows.parquet`/`labels.csv`/`meta.json`, so a researcher who wants
different windowing, different features, or raw-packet-level analysis can
re-derive from source rather than being limited to the shipped feature set.
(The clock-sync log files used only to compute the offset are also present
per episode but are an implementation detail rather than a modeling input.)

**Is the software used to preprocess/clean/label the instances available?**
Yes, as part of the VESPER-SH pipeline: `scripts/dataset/clock_sync.py`
(offset computation), `scripts/dataset/event_features.py` (activity/device
blocks), `scripts/dataset/net_features.py` (network block, via `tshark`),
`scripts/dataset/labeling.py` (schedule-based labeling), and
`scripts/dataset/export_episode.py` (orchestrates all of the above into one
episode's `windows.parquet`/`labels.csv`/`meta.json`).

## 5. Uses

**Has the dataset been used for any tasks already?**
Two baseline detectors are trained and evaluated as part of this work: an
unsupervised **IsolationForest** (trained on benign windows of the training
homes only, thresholded at a target benign false-positive rate) and a
supervised **RandomForest** (trained on all labeled windows of the training
homes), both evaluated on the held-out `by_home` test split. This
establishes that the labels are learnable and that cross-home
generalization is a non-trivial, measurable axis — it is not intended as an
exhaustive benchmark of detector architectures. See the README's Baselines
section and `scripts/dataset/run_baselines.py` /
`scripts/dataset/baselines.py` for the exact methodology; numeric results
are reported in the accompanying paper and in `baseline_results.json` once
the dataset is generated, and are not reproduced in this datasheet to avoid
stating figures ahead of the actual run.

**Is there a repository that links to papers or systems that use the
dataset?**
Not yet — this is the dataset's first release, alongside its introducing
paper.

**What other tasks could the dataset be used for?**
- Benchmarking cross-environment (by-home) and cross-resident (by-model)
  generalization of smart-home intrusion/anomaly detectors.
- Studying fused activity+device+network features for IDS, versus
  network-only baselines.
- Unsupervised/semi-supervised anomaly detection research where only
  benign training data is assumed available.
- Robustness/domain-shift research using the provided grouped k-fold splits.
- As a reproducible-generation reference: the pipeline that produced it
  (structured logging → scheduled attacks → exporter → features/labels →
  splits) can be re-run with different home/resident/attack configurations
  to produce extensions.

**Is there anything about the composition, collection, or preprocessing
that might impact future uses?**
Yes — see §8 (Limitations) for the specific, honestly-stated properties
(simulated firmware, emulated Wi-Fi, single-station LAN topology, RF-vantage
capture scope, episode duration) that any downstream use should account
for.

**Are there tasks for which the dataset should not be used?**
- It should **not** be used as evidence of detector effectiveness against
  real RF hardware or real ESP32/Xtensa firmware execution — the underlying
  substrate is simulated/emulated (see §8).
- It should **not** be treated as a substitute for physical red-team
  evaluation or for compliance/certification claims about real devices.
- It should **not** be used to make claims about real human occupant
  behavior, privacy, or safety — "resident" behavior is LLM-generated
  synthetic activity, not a model of, or data about, real people (see §2).

## 6. Distribution

**Will the dataset be distributed to third parties?**
Yes, as a public research artifact accompanying the paper, after the
double-blind review period.

**How will it be distributed?**
During double-blind review, an anonymized archive (produced by
`scripts/dataset/package_release.py`, which asserts no author-identifying
strings are present before zipping) is made available through the venue's
anonymous-submission artifact channel. After acceptance, a permanent,
citable release (e.g., a Zenodo record with a DOI) is planned; the
de-anonymized citation and persistent link will be added to this datasheet
and the README at that time.

**When will it be distributed?**
The anonymized archive is available at submission/review time; the
permanent citable release follows acceptance.

**Will the dataset be distributed under a copyright or license, and/or
under applicable terms of use?**
Not yet finalized. A permissive license (e.g., CC BY 4.0) is anticipated
for the data, consistent with the code's MIT license, since the dataset
contains no real personal or third-party data — but this is a
recommendation, not a commitment already in force, and will be finalized
at release time.

**Have any third parties imposed IP-based or other restrictions on the
data?**
None known. All content is synthetically generated by the authors' own
pipeline.

**Do any export controls or other regulatory restrictions apply?**
None anticipated. The dataset contains only synthetic network traffic and
simulated device/activity logs generated inside an isolated
emulation/simulation environment; it does not target, capture, or expose
any real production network or infrastructure.

## 7. Maintenance

**Who will maintain the dataset?**
The VESPER-SH authors (anonymized for review).

**How can the maintainers be contacted?**
Withheld during double-blind review to preserve anonymity. A maintenance
contact and persistent identifier will be published with the camera-ready
release.

**Will the dataset be updated?**
Yes — as a versioned release. Because generation is reproducible (fixed
seeds for split generation; a logged, deterministic attack schedule per
episode; per-episode metadata recording the clock offset used), new
releases can add homes, resident models, runs, or attack classes using the
same pipeline without invalidating the schema documented here. Any breaking
schema change will be reflected in `schema.md` with a version note.

**Is there a limit on the retention of the data?**
No retention limit is planned.

**Will older versions of the dataset continue to be supported/hosted/
maintained?**
Yes, intended to be handled via the hosting platform's versioning (e.g.,
Zenodo version history) once the permanent release is minted.

**If others want to contribute to, extend, or build on the dataset, is
there a mechanism for them to do so?**
Not through a formal contribution process at initial release. The
generation pipeline itself is the extension mechanism: additional homes,
resident models, or attack classes can be added by following the same
structured-logging → scheduled-generation → export → split pipeline
documented in the README and in `scripts/dataset/gen_run.md`.

## 8. Limitations

Stated plainly, so downstream users can correctly scope their claims:

1. **Firmware is simulated, not real.** Devices run an open-source
   firmware simulator, not real ESP32/Xtensa hardware. Findings about
   device/automation behavior in this dataset should not be presented as
   evidence about real firmware execution.
2. **Wi-Fi is emulated, not real RF.** The 802.11 network is emulated via
   `mac80211_hwsim` + `wmediumd`, a Linux-kernel software radio-medium
   emulation — not a real over-the-air RF environment. Findings about
   RF/management-frame attacks in this dataset should not be presented as
   evidence about real-world RF propagation, interference, or hardware
   radio behavior.
3. **Single-station LAN emulation limits multi-client attack fidelity.**
   The testbed's LAN emulation is single-station, so genuinely
   multi-client attacks (e.g., DHCP-starvation, which requires many
   distinct clients competing for a shared address pool) do not propagate
   faithfully in this environment. Rather than include a version of that
   attack that would misrepresent its real mechanics, it was **replaced**
   with a single-station-faithful `lan_scan` class (a SYN/port scan and
   flood from the station's real MAC, which *does* propagate correctly
   through a single-station topology).
4. **The RF monitor vantage sees only injected frames, not benign RF
   idle.** `rf.pcap` (the `wlan2` monitor-mode capture) captures the
   RF/management-layer attacks as they are injected, but the software
   radio-medium emulator does not relay ordinary benign AP/station traffic
   to a monitor-mode radio the way real RF propagation would. Consequently,
   there is no captured "benign RF idle" baseline in `rf.pcap` — the benign
   network baseline for this dataset comes from the AP-side capture
   (`ap.pcap`), which does see benign LAN traffic plus the LAN-visible
   *effects* of RF attacks (e.g., station disassociation). This is a
   property of the testbed's capture topology, documented here rather than
   left implicit; it should be accounted for by anyone building a
   detector that expects a benign RF baseline.
5. **Episodes are minutes long, not SWaT's multi-day continuous captures.**
   Each episode covers one bounded simulation run rather than days of
   continuous plant operation. VESPER-SH does not compete with SWaT/WaDI/HAI
   on single-environment temporal depth; it offers a different axis instead
   — many diverse homes and resident behaviors, reproducibly regenerable,
   with exact attack-interval ground truth — and that tradeoff is stated
   here explicitly rather than left for a reader to discover.

None of the above are hidden implementation quirks discovered after the
fact — they are testbed properties acknowledged up front, and they define
the scope within which VESPER-SH's cross-environment generalization claims
should be read.
